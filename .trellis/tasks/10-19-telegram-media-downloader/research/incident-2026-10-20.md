# 2026-10-20 Bot incident: available local evidence

## Scope and method

User requested the 17:00–18:30 Asia/Shanghai window and reported a successful
test around 17:10. Docker was initially stopped; the user started the engine.
Only container names/state, selected creation/logging metadata and bounded
historical stdout/stderr were inspected. Raw logs were captured only in memory
and reduced to fixed marker counts/timestamps, never echoed or saved. No real
Telegram request was initiated, no service was restarted/recreated, and no
configuration, secret or media content was read.

Application task/attempt records were additionally inspected using a read-only
SQLite connection with query_only enabled against the existing local Docker
database. Queries selected only state, mode, timestamps and fixed error codes;
no settings, credentials, title, caption, file path or Telegram personal IDs.

Both current project containers use Docker json-file logging, max-size 10m and
max-file 3. Docker retention applies to each container; it does not preserve a
removed/recreated container's history in its replacement. No old project
containers appeared in docker ps -a. Runtime files found under the local native
and Docker working directories were build/test logs, not a Bot request audit
covering the incident. Application source had no persistent diagnostic event
sink and normally swallowed/classified upstream failures for status display.

## What cannot be concluded

No first 401/429/409/network error is available from this evidence. Neither
ban timing nor Bot-versus-owner causality can be determined. The cancelled
task's updated_at alone does not identify whether cancellation came from the
Bot or WebUI. The oversize failure before a later successful download does not
prove any relation to subsequent enforcement. No media-content or token-leak
assessment was performed here.

## Follow-up

Implement default persistent, bounded, sanitized diagnostic events under the
application data volume and authenticated WebUI export. Preserve first failure,
error classification, retry deadlines and recovery transitions; omit raw
exceptions/URLs, credentials, media content, filenames and personal chat data.
New logging cannot retroactively reconstruct this missing historical error.
