# 运维与故障处理

执行下列 Compose 命令时选择实际使用的完整文件（直连 `compose.yaml`，代理 `compose.proxy.yaml`）。Windows Docker 的隔离应用重建及同文件系统停服备份恢复已验证，见 [Docker 隔离验收](docker-acceptance.md)；真实 NAS、Bot API 缓存、跨设备恢复和升级演练尚未验收。

默认 `compose.yaml` 启动应用和常驻 API 管理组件；云端不启动 API 子进程，无凭据时管理组件等待。日常凭据、模式切换及 API 子进程重启在 WebUI 完成，页面显示任务等待、切换、冷却和失败状态。`--profile local-api` 旧命令仍兼容，但不再需要。下文缓存、不确定获取和 TUN 维护针对本地模式；云端流式下载不保留本地 API 获取槽。不能同时运行多个 Bot 消费者，详见 [部署指南](deployment.md#从云端-api-迁移)。

通常使用 WebUI 切换，无需设置环境覆盖。若管理员通过 `TGD_BOT_API_MODE` 强制模式，必须先完成所有下载和恢复阻塞任务，再停服修改变量并重启；WebUI 的事务保护不能覆盖管理员修改环境后重启的操作。环境固定字段在 WebUI 只读，移除覆盖后才可在页面修改。

## 日常状态

WebUI 查看任务、逐文件结果和系统诊断。容器级检查：

```sh
docker compose --env-file .env -f compose.yaml ps
docker compose --env-file .env -f compose.yaml logs --tail 100 app
```

日志限制单文件 10 MB、保留 3 份。默认禁用 HTTP 访问日志和官方 API 详细日志，网络组件也不输出包含凭据的原始 sing-box 错误。不要发布 `.env`、Bot API 缓存内部目录、`/data` 密钥或 `desired.json`。故障报告只附脱敏错误码、版本和任务状态。

成功保存与 Telegram 通知分别记录；通知失败不代表媒体失败，不应反复下载媒体。媒体被人工移走或删除后，可重新发送请求；应用验证原路径不存在后允许重下。

下载任务支持单条或当前页多选删除，确认后仅移除已结束任务的记录展示，**保留下载文件**及去重、恢复所需的历史数据。活动任务请先取消，待取消完成后再删除；批量中有任务未结束或已不存在时整批不执行。删除后重新发送同一媒体，仍会检查已保存文件并避免重复下载；旧 Bot 按钮会提示记录已删除。尚未发送的任务通知停止发送，已经发出的消息不会撤回。

## Telegram 请求等待与认证暂停

云端与本地模式均启用请求保护，不需要额外配置。默认将 Bot 请求起始时间错开约 1 秒，同一私聊发送消息至少间隔 1.1 秒、群聊至少 3.1 秒；下载并发设置保持原值。这些是本项目的保守策略，不是 Telegram 承诺的安全阈值，也不保证账号不会受限。

系统状态中的 Bot 卡片会显示以下情况，设置页本地 API 状态也会显示当前请求保护原因：

| 状态 | 处理方式 |
| --- | --- |
| 请求限流，等待恢复 | 遵守 Telegram 返回的等待时间，自动等待；不要反复点校验或切换模式 |
| 连接异常，稍后重试 | 网络异常逐步延长重试间隔，检查代理和网络，等待页面显示的时间 |
| 认证异常，已暂停请求 | 检查 Bot Token；必要时更新并保存，再到系统状态使用“重试 Bot 连接” |

同一凭据的冷却、认证暂停保存在数据库中，重启应用、修改代理或云端/本地切换不会清除。手动恢复只验证已保存的 Bot 配置，至少间隔 60 秒；不会跳过服务器冷却、触发云端退出或解除迁移屏障。单个用户屏蔽机器人造成的消息发送失败，不会暂停整个 Bot。上游机器人认证失败也不等于 WebUI 管理员登录失效，更不能直接判断个人 Telegram 账号被封禁。

切换本地 API 前若凭据验证被拒绝，切换会显示失败，允许修改 Token；确认尚未退出云端且没有冷却时，可先手动恢复已保存凭据的连接，再重试切换。连接恢复不会自动切换模式，也不会重放结果未知的退出操作。

暂停期间停止新的上游请求，任务和待发通知继续保留；已进行的本地复制可以继续，既有本地 API 获取仍按原恢复规则处理，不能把暂停当作已取消上游获取。不要删除数据库、改 Token 或反复重启来绕过等待。只将自己有权保存的媒体发送给私人白名单 Bot，不公开本地 API 端口或分享 Token/API Hash。

本次保护约束应用主动发起的请求，不代表停止本地官方 API 服务内部的所有网络连接。官方仍可按行为和内容限制 Bot 及关联账号，参见 [调用频率说明](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this) 和 [开发者条款](https://telegram.org/tos/bot-developers#10-termination)。

## 目录权限、缺盘、空间不足

NAS 目录与容器目录不同：WebUI 根目录是 `/downloads`。检查宿主机下载挂载、目录标识及 UID/GID，确认 API 缓存能由应用只读打开。不要通过改为 root、开放 777、替代下载路径或移除只读挂载解决问题。

媒体共享掉挂载时，暂停下载并恢复原挂载；不要在底层空目录继续写入。应用数据目录不要和媒体共享同时失去持久化。对于 SMB/NFS 挂载，部署时确认断线行为、fsync 及不覆盖发布能力；未实测时不能保证文件系统语义。

峰值空间包含 API 的完整源文件、目标临时文件、已完成媒体和 API 会话缓存。同盘意味着多份文件竞争同一剩余空间，跨盘则两边都需要预算；未知大小文件无法事先精确预估。出现 ENOSPC/只读/权限错误后先解决空间或挂载问题，再手动重试失败项，禁止覆盖已有媒体。

## 获取阶段取消和重启恢复

`getFile` 触发的官方 API 后台获取不一定随 HTTP 客户端取消而终止。本项目采用保守策略：取消中的获取继续占用并发槽；不能仅因客户端断开就视作已取消。保存阶段在复制块边界检查取消，并清理应用自己的临时文件。

应用崩溃时无法可靠查询旧官方 API 获取的状态，未确定的任务可能显示 `recovery_blocked` 并保留槽位。先暂停并等待其他活动任务，按诊断说明重启 **bot-api**；入口写入新的 API generation 标识，应用据此解除旧获取的不确定状态。不要只清空数据库状态或盲目加并发。API 重启对 TDLib 缓存和后台任务的实际行为仍需 V-06 实测验证，未验收前该流程是保守恢复机制，不能宣称完整下载续传。

```sh
docker compose --env-file .env -f compose.yaml restart bot-api
```

代理模式同样可重启 `bot-api`；如果网络容器本身被**重建**而不是普通重启，需要将 API 与其一起重建，参见部署文档。

## 代理变更失败

- pending 表示新修订尚未通过执行链路，不代表已生效；failed 保留安全错误码。
- `proxy_validation_failed`：检查 HTTP CONNECT/SOCKS5 类型、主机解析、端口、凭据和 sing-box 配置兼容性。
- `proxy_live_check_failed`：候选链路未完成真实 Telegram TLS 请求，旧配置会尝试恢复。检查代理规则、认证和外网；不会切换直连。
- `proxy_process_exited`：代理进程退出，防火墙保持拒绝直连。修复后在 WebUI 重新保存新修订或重建服务。
- `redeploy_direct_stack`：需要停止旧栈，用直连 Compose 重建；不能仅在 WebUI 关闭按钮后假定已直连。

代理端点为域名时，在应用配置时解析为一个 IPv4。IP 变更后重新提交配置；暂不做自动 DNS 轮换。宿主机代理 `localhost` 不等于容器 localhost，使用 `host.docker.internal` 或可达的 LAN 地址。

## API 缓存维护

应用不删除官方 API 缓存内部文件，没有不可靠的在线“清缓存”按钮。先暂停新任务，等待所有获取/保存结束并确认没有不确定获取；停止应用与 API（代理栈连网络组件一起停止）。备份整个缓存目录后，根据所用官方 API/TDLib 版本支持的维护方式操作。无法确认哪些内部文件可安全删除时，保留缓存并扩容。

确需重新创建空缓存时，停服后**保留/改名备份旧缓存目录**，创建同权限的新目录再启动；这会丢失本地 API 会话与缓存，可能影响待处理更新和未完成获取，需要重新连接及恢复验证。不要在运行期间选择性删除官方会话数据库或文件；不要把“缓存已经重建”当作所有 Bot 更新完整性已验证。应用的最终媒体目录不随缓存维护删除。

## 备份与恢复

1. 暂停入口并等待任务完成；停止 Compose 栈，保证 SQLite 与加密设置一致。
2. 一起备份 `.env`、应用数据目录（数据库及 WAL/SHM 若有、加密密钥、配置）、媒体目录、私有 `TGD_HOST_API_CONTROL` 目录及需要保留的 API 数据目录。代理模式另备份网络目录。控制目录含独立交接密钥，不能公开或与不匹配的数据混用。使用 NAS 快照或可靠备份工具，限制备份访问权限。
3. 记录应用/本地 API/网络镜像 ID 或仓库 digest、架构、Compose 文件与源码 revision。密钥丢失无法恢复加密凭据。
4. 恢复到相同容器路径及 UID/GID，先检查挂载与权限，再启动单实例。用测试文件验证队列、通知、去重和原文件存在性。

不要在应用运行时只复制 `*.db` 而忽略 WAL，或只恢复数据库而丢失对应加密密钥。未提供跨版本任意数据库降级保证。

## 升级与回滚

升级前查看变更、做停止写入的一致性备份，并保留旧镜像。更新固定源码/镜像版本后先执行 Compose 静态验证和构建，再在测试环境验证迁移。生产执行停止旧栈并启动新栈；迁移失败保留数据和诊断，不能跳过 migration 直接消费任务。

失败回滚使用匹配旧镜像的数据库、密钥和配置备份，不是仅切回旧镜像。重建容器不删除持久化目录；不要使用 `down -v`、清理未知目录或运行数据库降级来猜测修复。备份恢复、固定镜像升级及飞牛 OS 实机演练结果记录在 [验证记录](verification.md)。
