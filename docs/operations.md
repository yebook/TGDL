# 运维与故障处理

更新已有部署、保留配置与数据及失败回退，请使用 [版本升级指南](upgrade.md#upgrade)；下载目录变更后的重新登记见下文 [下载目录身份登记](#storage-identity)。

日常沿用部署时的 Compose 与环境文件：使用 `compose.yaml` 从源码构建；直连、代理及 API 模式都在 WebUI 设置。Windows Docker 的隔离应用重建及同文件系统停服备份恢复已验证，见 [Docker 隔离验收](docker-acceptance.md)；真实 NAS、完整内置代理、跨设备恢复和升级演练尚未验收。

标准栈启动应用与 API 管理服务；无凭据时 API 进程等待，私有卷由一次性初始化服务准备。日常凭据、代理开关、模式切换及 API 子进程重启在 WebUI 完成，页面显示等待、切换、冷却和失败状态。下文缓存和不确定获取针对本地模式；云端流式下载不保留本地 API 获取槽。不能同时运行多个 Bot 消费者，详见 [部署指南](deployment.md#后续接入本地-api)。

通常使用 WebUI 切换，无需设置环境覆盖。若管理员通过 `TGD_BOT_API_MODE` 强制模式，必须先完成所有下载和恢复阻塞任务，再停服修改变量并重启；WebUI 的事务保护不能覆盖管理员修改环境后重启的操作。环境固定字段在 WebUI 只读，移除覆盖后才可在页面修改。

## 日常状态

最顶部与账户操作位于同一顶栏显示连接、活动与等待文件数、剩余空间，任务页查看逐文件结果。连接异常到「设置 → 连接 Telegram」，保存位置及空间详情到「下载与保存」，日志和备份到「维护与备份」。版本在导航栏左下角查看。状态刷新失败时不要把保留的上次结果当作当前正常。容器级检查：

```sh
docker compose --env-file .env -f compose.yaml ps
docker compose --env-file .env -f compose.yaml logs --tail 100 app
```

Docker 控制台日志限制单文件 10 MB、保留 3 份，重建容器后不能依靠新容器找回旧容器的日志。默认禁用 HTTP 访问日志和本地 API 详细日志，不输出包含凭据的原始错误。应用的持久诊断日志见下文。不要发布 `.env`、Bot API 缓存内部目录、`/data` 密钥或 `desired.json`。故障报告只附脱敏错误码、版本和任务状态。

成功保存与 Telegram 通知分别记录；通知失败不代表媒体失败，不应反复下载媒体。媒体被人工移走或删除后，可重新发送请求；应用验证原路径不存在后允许重下。

下载任务支持单条或当前页多选删除，确认后仅移除已结束任务的记录展示，**保留下载文件**及去重、恢复所需的历史数据。活动任务请先取消，待取消完成后再删除；批量中有任务未结束或已不存在时整批不执行。删除后重新发送同一媒体，仍会检查已保存文件并避免重复下载；旧 Bot 按钮会提示记录已删除。尚未发送的任务通知停止发送，已经发出的消息不会撤回。

## 持久诊断日志

日志默认启用。在 **设置 → 维护与备份 → 诊断日志** 查看日志状态，点击 **导出诊断日志** 下载最近的事件；不需要进入容器，也不会因此连接 Telegram。导出最多包含最近 1000 条记录，按时间顺序排列；较早内容被省略时会提示。尚无记录时会提示，不代表发生过的事件都能追溯。

完整滚动日志位于应用数据卷中的 `logs/events.jsonl`（容器内 `/data/logs/events.jsonl`）。每个文件最大 10 MiB，保留 3 个归档，加当前文件约 40 MiB。默认按事件时间保留最近 **7 天**；「设置」中的日志保留天数允许整数 **0–3650**，`0` 关闭按天清理，容量轮转始终生效。因此不保证保留满 7 天，容量满时更早轮转。容器重建只要沿用原数据卷，日志仍保留。

默认按应用设置的时区每天 **08:00** 清理一次，可在设置页修改为其他 `HH:MM` 时间。后台每分钟轻量检查是否到期，不依赖 Bot 在线；启动、修改保留策略或时区只安排下一个未来清理时间，不立即扫描，不补跑停机期间错过的清理。容量轮转始终有效。夏令时重复时间只执行首次，不存在的时间跳至下一天。

「维护与备份」显示日志总占用、文件数量、已生效保留天数、最近和下次清理时间。占用仅统计诊断日志文件，不包含数据库、API 缓存、媒体或 Docker 控制台日志。手动清理不改变每日计划。修改策略不会连接或校验 Bot；若清理失败，配置保存不会回滚，需按日志状态处理存储问题。

在 **设置 → 维护与备份 → 诊断日志** 点击 **清理诊断日志** 并确认，只清理诊断事件及待合并摘要，**不删除媒体、任务、配置、凭据、API 缓存，也不重置请求冷却或认证暂停**。清理后记录一条 `logs_cleared` 事件并继续记录新日志，因此文件不会永久保持空白。导出与清理互斥，清理前如需留证请先导出；失败时页面显示错误，不视作已全部清理。

文件时间使用 UTC，字段带时区，例如 `09:06:21Z` 对应北京时间 `17:06:21`。排障时请提供当地时区和大致时间范围。

日志记录 Bot 调用异常分类、恢复、请求等待和下载结果，包含固定方法名、状态/错误码、耗时及内部任务编号。正常空轮询不逐条记录，重复异常会合并，因此不能将日志行数直接视为请求次数；首次异常立即记录，强制崩溃可能丢失尚未写入的重复次数摘要。记录不会包含 Token、API Hash、密码、原始异常和请求 URL，也不包含媒体正文、标题、文件路径或用户/聊天个人资料。导出不会自动上传；提交故障报告前仍建议自行检查内容。

日志写入失败时，下载业务不会因为日志故障被改判失败，「维护与备份」会显示日志异常。日志使用应用数据卷；慢盘或失联的数据卷可能延长调用及停服等待，建议将应用数据目录放在稳定可写的存储上。检查应用数据卷空间、挂载和原 UID/GID 权限，修复后再观察；不要删除数据库、密钥或修改媒体文件来解决日志问题。诊断日志仅保存启用后的事件，无法补回旧版本未记录或已淘汰的历史。

常见错误需要结合时间线理解：`401` 表示凭据被拒绝，不能单独证明 Bot 被封；`429` 表示限流，按等待期限处理；`409` 可能表示重复消费者或更新接收方式冲突；网络异常不等于账号封禁。客户端通常拿不到平台内部的审核原因，日志只能辅助定位首次异常和后续行为。

## Telegram 请求等待与认证暂停

云端与本地模式均启用请求保护，不需要额外配置。默认将 Bot 请求起始时间错开约 1 秒，同一私聊发送消息至少间隔 1.1 秒、群聊至少 3.1 秒；下载并发设置保持原值。这些是本项目的保守策略，不是 Telegram 承诺的安全阈值，也不保证账号不会受限。

顶部状态摘要和「设置 → 连接 Telegram」会提示以下情况；在连接分区查看完整原因并处理：

| 状态 | 处理方式 |
| --- | --- |
| 请求限流，等待恢复 | 遵守 Telegram 返回的等待时间，自动等待；不要反复点校验或切换模式 |
| 连接异常，稍后重试 | 网络异常逐步延长重试间隔，检查代理和网络，等待页面显示的时间 |
| 认证异常，已暂停请求 | 检查 Bot Token；必要时更新并保存，再到「设置 → 连接 Telegram」使用“重试 Bot 连接” |

同一凭据的冷却、认证暂停保存在数据库中，重启应用、修改代理或云端/本地切换不会清除。手动恢复只验证已保存的 Bot 配置，至少间隔 60 秒；不会跳过服务器冷却、触发云端退出或解除迁移屏障。单个用户屏蔽机器人造成的消息发送失败，不会暂停整个 Bot。上游机器人认证失败也不等于 WebUI 管理员登录失效，更不能直接判断个人 Telegram 账号被封禁。

切换本地 API 前若凭据验证被拒绝，切换会显示失败，允许修改 Token；确认尚未退出云端且没有冷却时，可先手动恢复已保存凭据的连接，再重试切换。连接恢复不会自动切换模式，也不会重放结果未知的退出操作。

暂停期间停止新的上游请求，任务和待发通知继续保留；已进行的本地复制可以继续，既有本地 API 获取仍按原恢复规则处理，不能把暂停当作已取消上游获取。不要删除数据库、改 Token 或反复重启来绕过等待。只将自己有权保存的媒体发送给私人白名单 Bot，不公开本地 API 端口或分享 Token/API Hash。

本次保护约束应用主动发起的请求，不代表停止本地官方 API 服务内部的所有网络连接。官方仍可按行为和内容限制 Bot 及关联账号，参见 [调用频率说明](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this) 和 [开发者条款](https://telegram.org/tos/bot-developers#10-termination)。

## 目录权限、缺盘、空间不足

如果启动日志提示无法读取 `/app/entrypoint.py` 或 `/usr/local/lib/tgd-api-supervisor.py`（`Permission denied`），错误涉及镜像内程序文件。旧构建可能继承了 NAS 源码目录的严格文件权限；更新到修复后的源码并重新构建应用与 API 运行镜像，再重新创建容器。仅重启原容器不会改变镜像内权限，也不需要清空数据、下载文件或 API 缓存。修复在镜像打包阶段设置程序权限，不需要将数据目录开放为 777 或改用 root。

例如镜像中的脚本为 root 所有、权限为 `-rwx------`（700），容器使用 `1000:1000` 时就无法读取；父目录即使为 755 也不能解决文件本身的限制。当前构建在最终复制后显式设置权限，不只依赖 `COPY --chmod`。源码部署取得修复后，在项目目录执行：

```sh
docker compose build app bot-api
docker compose up -d --no-build --force-recreate
```

这会更新容器使用的镜像并重新创建容器，API 初始化服务与本地 API 共用新镜像；无需重新编译 TDLib。ZIP 更新时保留自己的 `.env` 和全部业务目录，不要用模板覆盖。

若初始化容器仍提示 `TGD_UID and TGD_GID must be nonroot numeric IDs`，说明运行镜像中仍是旧版初始化脚本；当前版本允许 UID/GID 为 0。先更新源码或镜像并重新创建容器，而非反复修改 UID/GID。镜像标签同为 `0.1.0` 或显示最近构建，不代表内容已经更新。

NAS 目录与容器目录不同：WebUI 根目录是 `/downloads`。检查宿主机下载挂载、目录标识及 UID/GID，确认 API 缓存能由应用只读打开。推荐使用有目录权限的普通用户；UID/GID 支持 `0`，但容器移除 capabilities，仍需正确配置目录权限。不要通过开放 777、替代下载路径或移除只读挂载解决问题。

媒体共享掉挂载时，暂停下载并恢复原挂载；不要在底层空目录继续写入。应用数据目录不要和媒体共享同时失去持久化。对于 SMB/NFS 挂载，部署时确认断线行为、fsync 及不覆盖发布能力；未实测时不能保证文件系统语义。

峰值空间包含 API 的完整源文件、目标临时文件、已完成媒体和 API 会话缓存。同盘意味着多份文件竞争同一剩余空间，跨盘则两边都需要预算；未知大小文件无法事先精确预估。出现 ENOSPC/只读/权限错误后先解决空间或挂载问题，再手动重试失败项，禁止覆盖已有媒体。

## 下载目录身份登记 {#storage-identity}

应用数据目录中的 `storage-identity-<根目录ID摘要>.json` 记录下载目录的文件系统设备号与 inode，用于阻止挂载丢失、目录替换后误写入其他位置。重建容器但沿用原目录无需重新登记；迁移到新目录、更换设备或网络文件系统身份变化时，先核对实际挂载，再处理身份不一致提示。

1. 等待下载、保存结束，停止服务，备份应用数据与媒体目录。
2. 确认 Compose 挂载指向预期目录，迁移后的已有媒体完整、目录可访问且权限正确；挂载异常时先恢复挂载。
3. 仅删除**应用数据目录**中对应根目录的身份 JSON，保留数据库、密钥和媒体。默认根目录 ID 为 `default`，文件为 `storage-identity-37a8eec1ce19687d.json`；其他根目录须核对其 ID 的 SHA-256 前 16 位，不要通配删除所有身份文件。
4. 启动服务，应用会登记已确认的新目录。核对存储状态与已有文件，再用小文件验证保存。

不要在挂载异常时删除身份记录，也不要清空数据目录来解除提示。旧开发版本的格式调整仅按对应 [版本说明](changelog.md#storage-identity-011) 处理，不是每次升级的必做操作。

## 获取阶段取消和重启恢复

`getFile` 触发的官方 API 后台获取不一定随 HTTP 客户端取消而终止。本项目采用保守策略：取消中的获取继续占用并发槽；不能仅因客户端断开就视作已取消。保存阶段在复制块边界检查取消，并清理应用自己的临时文件。

应用崩溃时无法可靠查询旧官方 API 获取的状态，未确定的任务可能显示 `recovery_blocked` 并保留槽位。先暂停并等待其他活动任务，按页面诊断使用「重启 API 进程」或专门的恢复操作；标准受管理部署优先使用 WebUI，不直接绕过任务保护。只有服务确认新的进程实例后，才能按恢复流程处理旧获取的不确定状态。不要只清空数据库状态或盲目加并发。API 重启对 TDLib 缓存和后台任务的实际行为仍需真实环境验证，不能宣称完整下载续传。

仅管理服务容器自身故障、WebUI 无法处理时，才在确认安全边界后进行 Docker 维护，参见部署文档。

## 代理变更失败

- pending 表示新修订尚未通过执行链路，不代表已生效；failed 保留安全错误码。
- 代理状态来自实际连接或匹配的 API 进程配置与新鲜心跳，不能仅凭保存成功判断生效。
- 检查 HTTP CONNECT / SOCKS5 类型、主机解析、端口、认证以及容器是否能访问代理；代理软件需允许 Docker 网络访问。
- 本地代理变更在排空后重启 API 子进程；修改日志保留等无关设置不会重启进程，也不会重新退出云端。
- 配置或连接失败时不会自动改为直连。修正后通过页面重试；关闭代理需明确关闭并保存，随后使用容器默认出口。

宿主机代理 `localhost` 不等于容器 localhost，使用 `host.docker.internal` 或可达的 LAN 地址。代理端点自身的域名仍由容器 DNS 解析，不应理解为所有 DNS 和 WebUI 流量都经过代理。

## API 缓存维护

标准部署自动清理**已安全保存的媒体缓存**：本地 API 先下载到缓存，应用复制到最终目录，完成大小、哈希校验与持久化后，再通过 TDLib 删除对应缓存文件。API 的会话、认证及运行数据库保留；这不是清空整个 `bot-api` 目录，也不删除 Telegram 消息或已归档媒体。下载和保存期间仍可能同时占用两份空间，跨磁盘也适用。

为避免其他任务仍在读取同一缓存，清理会等待当前本地获取与保存结束，期间暂缓领取新的本地下载任务。清理记录持久化，应用重启后继续处理。清理失败独立退避重试，已保存任务仍保持成功，不会因此重新下载；诊断日志会记录清理结果。若最终文件丢失、被修改或存储不可用，则保留缓存，不删除可能仅剩的一份。失败或取消任务的缓存不会在此流程中提前删除。

自动清理需要项目配套构建的本地 API；自定义外部标准 Bot API 没有该私有接口，不能保证自动清理。更换 Bot 或切到云端后，旧 Bot 的待清理记录保留，恢复对应本地连接后继续。此功能处理新保存文件，不扫描清空已有历史缓存。缓存仍占用较大时，先检查诊断日志和连接状态，不要直接剪切 API 内部文件。

确需重新创建空缓存时，停服后**保留/改名备份旧缓存目录**，创建同权限的新目录再启动；这会丢失本地 API 会话与缓存，可能影响待处理更新和未完成获取，需要重新连接及恢复验证。不要在运行期间选择性删除官方会话数据库或文件；不要把“缓存已经重建”当作所有 Bot 更新完整性已验证。应用的最终媒体目录不随缓存维护删除。

## 备份与恢复

仅需迁移平台配置时，使用 WebUI 的[加密配置备份与恢复](configuration-backup.md)。它包含可编辑的密钥配置，但不包含管理员账号、任务、数据库、媒体、日志和 API 缓存。以下步骤针对需要这些数据的完整停服备份。

1. 暂停入口并等待任务完成；停止 Compose 栈，保证 SQLite 与加密设置一致。
2. 一起备份 `.env`、应用数据目录（数据库及 WAL/SHM 若有、加密密钥、配置）、媒体目录及需要保留的 API 缓存，同时备份 `api-control` 私有命名卷。实际卷名可通过 Compose 的卷列表核实；使用支持 Docker 卷的停服备份工具。控制卷含独立交接密钥和加密指令，不能公开或与不匹配的数据混用；勿将命名卷遗漏或执行 `down -v`。
3. 记录应用和本地 API 镜像 ID 或仓库 digest、架构、Compose 文件与源码 revision。保留对应完整源码与实际部署的 `.env`。密钥丢失无法恢复加密凭据。
4. 恢复到相同容器路径及 UID/GID，先检查挂载与权限，再启动单实例。用测试文件验证队列、通知、去重和原文件存在性。

不要在应用运行时只复制 `*.db` 而忽略 WAL，或只恢复数据库而丢失对应加密密钥。未提供跨版本任意数据库降级保证。

## 查看空闲 CPU 占用

在部署目录执行下面的命令，分别查看 `app` 与 `bot-api` 的 CPU 用量：

```sh
docker stats --no-stream
```

关闭 WebUI 页面，等待下载、缓存清理和 API 切换结束后，隔一段时间多观察几次，再与下载时的用量对比。浏览器打开时会定期请求任务和连接状态，不能作为完全空闲的基线。

本地模式下，Bot API 仍会维护 Telegram 连接，空闲 CPU 不一定为零。排查时记录各容器的用量、API 模式、任务数量，以及是否存在连接重试、缓存清理或日志维护；比较更新前后时使用相同条件。
