# 运维与故障处理

日常连接、下载、日志和备份都可以在 WebUI 中管理。更新已有部署请按 [版本升级指南](upgrade.md#upgrade) 操作；移动下载目录后，请阅读 [下载目录身份登记](#storage-identity)。

## 日常状态

顶栏显示连接、活动与等待文件数、剩余空间。连接异常时前往「设置 → 连接 Telegram」，查看保存位置和缓存时前往「下载与保存」，日志和备份位于「维护与备份」。应用版本在导航栏底部查看。

如果页面无法访问，在原部署目录执行：

```sh
docker compose ps -a
docker compose logs --tail 100 app bot-api init-volumes
```

`init-volumes` 成功完成后退出是正常现象，`app` 和 `bot-api` 应保持运行。状态刷新失败时，页面保留的上次结果可能已过时。

下载完成但 Bot 没有通知时，先查看任务详情和实际文件。通知失败不会使已保存文件失效，无需重复下载。同一个 Bot 只能由一套程序接收消息。

任务删除默认保留文件，也可勾选「同时删除已下载文件」。共享文件、被替换的文件和无法安全访问的文件可能会保留，请以操作结果为准。文件状态的含义见 [任务说明](usage.md#本地文件与删除任务)。

## 持久诊断日志

在 **设置 → 维护与备份 → 诊断日志** 查看占用、保留策略和清理时间，点击 **导出诊断日志** 下载最近的事件。导出最多包含最近 1000 条记录，不会自动上传。

默认保留最近 **7 天**，每天按应用时区在 **08:00** 清理。可设置保留天数 **0–3650**，`0` 关闭按天清理；容量轮转仍会生效，每个文件最大 10 MiB，保留 3 个归档，加当前文件约 40 MiB。日志较多时，实际可追溯时间可能短于设置天数。

完整日志位于应用数据目录的 `logs/events.jsonl` 及其归档。重建容器时沿用原数据目录即可保留。Docker 控制台日志另行轮转，不能替代持久诊断日志。

点击 **清理诊断日志** 并确认，只清理诊断事件，不删除媒体、任务、配置、凭据或 API 缓存，也不重置请求等待。需要排障时先导出，再清理；清理后会继续记录新事件。

排障时记录当地时区和大致发生时间。日志时间使用 UTC，例如 `09:06:21Z` 对应北京时间 `17:06:21`。重复异常会合并，日志行数不等于请求次数；日志无法补回启用前或已被清理的事件。

日志不记录 Token、API Hash、密码、原始请求地址、媒体内容或个人聊天资料。反馈前仍请检查导出内容，只提供版本、任务编号、错误码和相关脱敏事件，不要上传 `.env`、数据库、密钥或 API 缓存。

日志写入失败时，先检查应用数据目录的剩余空间、挂载和 UID/GID 权限。日志故障不会将已保存的媒体改判为失败，不要通过删除数据库或媒体解决日志问题。

### 常见错误怎么处理

| 错误或状态 | 含义与处理 |
| --- | --- |
| `401`、认证暂停 | 检查 Bot Token，必要时更新后保存，再重试 Bot 连接；不能仅据此认定 Bot 被封禁 |
| `429`、请求限流 | 按页面给出的期限等待，不反复重启或切换模式 |
| `409`、消息接收冲突 | 停止其他使用同一 Bot 的程序，检查是否仍有旧部署运行 |
| `pacing`、等待请求间隔 | 应用正在有序安排请求，会自动继续，无需修改代理 |
| `backoff`、连接异常稍后重试 | 检查网络与代理，等待自动重试；持续失败时查看前面的错误 |
| `protection_unavailable` | 检查应用数据目录空间、挂载和读写权限 |
| `LOCAL_API_START_FAILED` | 查看对应原因，检查 API 凭据、容器状态和缓存目录权限，再重试连接 |
| `TELEGRAM_REJECTED`、`BAD_REQUEST` | 文件获取被拒绝，结合诊断中的原因处理，不能只凭 HTTP 400 判断为网络故障 |

本地文件获取被拒绝时，`getfile_file_id_missing`、`getfile_file_id_invalid` 和 `getfile_file_too_big` 分别对应缺少文件标识、文件标识无效和大小限制。不明确的原因请保留错误码与发生时间，通过 [Issues](https://github.com/yebook/TGDL/issues) 反馈。

## 网络连通诊断

在「设置 → 连接 Telegram」点击 **检测网络连通性**，检查部署容器当前使用的直连或代理线路。请从实际运行 TGDL 的部署中发起检测；电脑能打开 Telegram 网页，不代表容器使用的线路也可用。

| 观察结果 | 下一步 |
| --- | --- |
| Telegram 与 Google HTTPS 均可达 | 应用的 HTTPS 出口正常；本地模式还需查看 Telegram 协议结果和 API 错误 |
| 仅 Telegram HTTPS 失败 | 检查该目标的路由、代理规则和防火墙 |
| 仅 Google 失败 | 检查该目标线路，不必因此判断 Telegram 不可用 |
| 两者均失败 | 检查容器网络、DNS、代理地址、端口和认证 |
| 本地 API 端口不可达 | 检查 `bot-api` 容器状态和 Compose 内部网络 |
| HTTPS 可达、Telegram 协议失败 | 检查本地 API 容器的出口、防火墙和代理规则 |
| 只有部分协议目标可达 | 按页面列出的地址和端口分别排查 |
| 协议可达但 Bot 仍无法使用 | 检查凭据、配置应用状态和最新 API 错误 |
| 检测组件不可用 | 确认应用和配套 API 来自同一版本，等待连接配置应用后重试 |

网络检测不会修改配置、重启 API 或清除请求等待。线路可达也不代表 Token 有效；连接恢复后，可向 Bot 发送 `/start` 检查回复。

NAS 可以直连 Telegram 时无需配置代理。确需使用宿主机代理时，填写容器可访问的 `host.docker.internal` 或局域网地址，并允许 Docker 访问该端口。容器内的 `127.0.0.1` 指向容器自身，系统和浏览器代理不会自动应用到容器。

### 网络恢复后怎样重连

1. 在「设置 → 连接 Telegram」查看当前状态。修改代理时先保存，并等待新配置应用。
2. 网络已恢复、配置未变，但仍显示操作失败时，点击 **重试操作**。重试使用已保存的配置。
3. 本地 API 需要重新启动时，点击 **重启 API 进程** 并确认。后台会等待当前请求安全结束，无需重建容器；云端模式无需启动本地进程。
4. 等待切换完成后，向 Bot 发送 `/start`，再发送一张图片确认能够正常保存。仍失败时，查看最新错误和诊断日志。

网络恢复不会清除 Telegram 限流或云端冷却。若提示「云端退出结果待确认」，先检查是否仍有其他程序使用该 Bot，再按页面的专门确认流程处理，普通重试不能代替确认。

## Telegram 请求等待与认证暂停

云端和本地模式都启用请求保护，无需额外配置。出现等待时，任务和待发通知会保留。

| 页面提示 | 处理方式 |
| --- | --- |
| 请求限流，等待恢复 | 按页面时间等待，不反复校验或切换模式 |
| 连接异常，稍后重试 | 检查网络或代理，等待自动重试 |
| 认证异常，已暂停请求 | 检查 Bot Token，必要时更新并保存，再点击「重试 Bot 连接」 |

同一 Bot 的等待和认证暂停会保留，重启、修改代理或切换 API 不会清除。手动恢复连接至少间隔 60 秒，仍需遵守服务器等待时间。

不要删除数据库、反复改 Token 或重启来跳过等待。只让明确授权的用户使用 Bot，按需要设置下载并发；请求保护不能保证 Bot 或关联个人账号不受限制，详见 [账号风险](faq.md#account-risk)。

## 目录权限、缺盘、空间不足

WebUI 中的 `/downloads` 是容器路径，宿主机实际位置由 `.env` 的 `TGD_HOST_DOWNLOADS` 决定。核对三个宿主目录的挂载及 UID/GID 权限，推荐普通用户运行，不要将整个数据目录开放为 `777`。

若日志提示无法读取镜像内的 `/app/entrypoint.py` 或 `/usr/local/lib/tgd-api-supervisor.py`，请按 [版本升级指南](upgrade.md) 更新源码并重新构建应用与 API 镜像。仅重启原容器不会更新程序文件权限，也无需清空数据或改用 root。

共享目录掉线时，暂停下载并恢复原挂载，不要在底层空目录继续写入。应用数据目录应使用可靠的本地存储，数据库不要放到 SMB/NFS 共享中。

本地下载和保存期间，API 缓存与目标文件会暂时各占一份空间。同盘时两份文件共享剩余容量，跨盘时两边都需留足空间。遇到空间不足、只读或权限错误，先恢复存储，再重试失败项。

## 下载目录身份登记 {#storage-identity}

TGDL 会记住下载目录，避免挂载丢失或目录被替换后将媒体写到错误位置。沿用原目录重建容器无需重新登记；移动目录、更换设备或恢复备份后出现身份不一致时，按以下步骤处理：

1. 等待下载、保存结束，停止服务，备份应用数据和媒体。
2. 核对 Compose 挂载、已有媒体和目录权限。挂载异常时先恢复挂载。
3. 仅删除**应用数据目录**中对应该下载根目录的身份 JSON。默认根目录 ID 为 `default`，文件为 `storage-identity-37a8eec1ce19687d.json`；自定义根目录需核对其 ID 的 SHA-256 前 16 位，不能通配删除全部身份文件。
4. 启动服务，核对存储状态和已有文件，再发送一个小文件确认保存位置。

保留数据库、密钥和媒体，不要在挂载异常时通过删除身份记录解除提示。早期开发版本的格式调整请按 [对应升级说明](changelog.md#storage-identity-011) 操作。

## 获取阶段取消和重启恢复

本地模式先将媒体下载到 API 缓存，再保存到目标目录。两阶段分别显示进度，下载达到 100% 后请等待保存完成。下载较慢或暂时没有进度时，不会仅因耗时较长就自动终止。

在任务详情点击 **取消下载**，等待显示 **已取消**。本地获取可能需要时间确认停止，期间显示 **取消中**。已保存文件会保留；其他任务仍在使用同一缓存时，不受当前取消影响。

网络中断或应用重启后，无法确定原下载是否仍在执行时，任务可能显示 **等待恢复**（`recovery_blocked`），并继续占用下载名额。连接恢复后会继续核对；必要时按页面提示使用 **重启 API 进程** 或专门的恢复操作，不要改数据库或盲目增加并发。

Bot 恢复连接与旧下载结束是两回事，因此「已就绪」和「等待恢复」可能同时出现。查看任务详情及诊断日志，按任务提示处理即可。应用与本地 API 应使用配套版本，升级时一起更新。

### 暂停、继续和断点续传

当前支持取消，暂不提供暂停、继续和可靠的断点续传。同一 API 进程再次获取同一媒体时，可能复用有效缓存，但不保证从上次位置继续；API 重启或缓存清理后可能需要重新下载。保存阶段取消后，再次保存会重新复制。

## 代理变更失败

- 检查 HTTP CONNECT / SOCKS5 类型、地址、端口和认证信息，确认容器能访问代理。
- 保存后等待页面显示配置已应用；仍在等待时不要连续提交其他方案。
- 配置失败时不会自动改为直连。修正后保存或按页面提示重试。
- 要恢复直连，请明确关闭代理并保存；本地模式会等待当前请求安全结束后重新连接。

代理只负责 Telegram 连接，不会自动代理 WebUI、镜像拉取和构建依赖下载。宿主机代理的域名也需要能从容器中解析。

## API 缓存维护

本地模式会在文件完整保存后自动清理对应媒体缓存，保留 API 会话和运行数据。清理会等待活动下载与保存结束，失败后独立重试，不影响任务已保存的结果。最终文件缺失、被修改或不可访问时，会保留缓存并提示原因。

在 **设置 → 下载与保存 → Telegram 媒体缓存**：

- 点击 **刷新占用**，查看当前 Bot 媒体缓存的实际磁盘占用及文件数量。下载期间也可刷新；显示的是最近一次读取结果。
- 点击 **清理媒体缓存** 并确认，清理取消、失败等情况留下的媒体缓存。已保存文件、任务、配置和 API 会话保留，再次下载被清理的媒体需要重新获取。
- 按钮不可用时，查看提示并等待下载、排队、恢复或连接操作结束。仅刷新占用不受这些清理限制。

有待自动清理的记录时，手动清理会先检查已保存文件。清理结果无法确认时会继续保留保护；可在连接设置中重启受管理 API 后再查看状态。

清理同时移除媒体目录中的空子目录，保留非空目录、Bot 工作根目录及运行数据。后续下载会自动创建需要的媒体目录。

这些功能需要项目配套的本地 API，自定义外部标准服务可能不支持。更换 Bot 或切到云端后，旧 Bot 的待清理记录会保留，恢复对应本地连接后继续处理。

不要在服务运行时手动剪切缓存文件或删除会话数据库。确需重建整个缓存目录时，先停服并将旧目录改名备份，再创建权限一致的新目录；这会丢失原 API 会话和未完成下载的缓存，需重新连接并处理待恢复任务。最终媒体目录不随缓存清理删除。

## 备份与恢复

只需迁移设置时，使用 [加密配置备份](configuration-backup.md)。需要同时保留账号、任务和媒体时，请进行完整停服备份：

1. 停止向 Bot 发送新媒体，等待下载、连接切换和缓存清理结束，再停止 Compose 服务。
2. 一起备份 `.env`、Compose 文件、完整应用数据目录、媒体目录、API 缓存和 `api-control` 私有命名卷。以 `.env` 中实际路径为准，备份放在部署目录之外。
3. 保留完整源码及当前镜像，记录版本、镜像 ID、架构和 Compose 项目名。应用数据中的数据库、WAL/SHM（若有）和加密密钥必须一起保存；私有卷也含密钥，请限制备份访问权限。
4. 恢复时先停服，使用同一份备份中的数据、密钥和私有卷，保持原容器路径与 UID/GID。核对挂载后启动单实例，检查任务、设置、已有文件及 Bot 回复。

不要在运行时只复制 `*.db`，也不要只恢复数据库而遗漏对应密钥。不要执行 `down -v` 删除私有卷。恢复到新目录或设备时，按 [下载目录身份登记](#storage-identity) 核对位置；跨版本回退请按 [升级指南](upgrade.md#upgrade) 恢复完整旧备份。

## 查看空闲 CPU 占用

在部署目录执行：

```sh
docker stats --no-stream
```

关闭 WebUI，等待下载、缓存清理和连接切换结束，隔一段时间观察 `app` 与 `bot-api` 的用量。浏览器打开时会自动刷新状态，本地 API 也会维护 Telegram 连接，空闲用量不一定为零。

持续偏高时，查看是否有连接重试、缓存清理或日志维护，并记录容器用量、API 模式和任务数量，随脱敏诊断一起反馈。
