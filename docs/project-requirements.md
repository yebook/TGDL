## 1. 项目定位与目标

为个人及有类似需求的自托管用户，提供一个通过 Telegram Bot 将视频、图片保存到本地或 NAS 的轻量工具。

用户在 Telegram 中发现希望收藏的媒体，将其转发或发送给专属 Bot，查看媒体信息并确认下载；系统在后台保存文件，并通过 Bot 反馈成功或失败。WebUI 用于初始配置、配置修改、任务查看和必要的管理操作。

设计原则：操作步骤少、部署简单、下载可靠、错误易理解。首版优先完成“接收媒体 → 确认 → 下载落盘 → 反馈 → 管理”的完整流程。

- 首版采用单实例、单 Bot、单管理员；Bot 使用者通过 Telegram 用户 ID 白名单控制。

## 3. 用户场景与首版边界

### 3.1 主要场景

1. 在手机中转发频道视频，确认后由 NAS 下载，无需先保存到手机再传输。
2. 将单张图片、文件形式的图片或媒体媒体组发送给 Bot，确认后归档。
3. 通过 Bot 收到结果，在 WebUI 查看进度、失败原因并重试。
4. 部署后通过 WebUI 修改应用配置，了解配置何时生效。

### 3.2 首版范围

| 分类 | 首版能力 |
| --- | --- |
| 输入 | Bot 私聊中的原生视频、照片，以及文件形式的受支持视频/图片。 |
| 授权 | 用户白名单、明确确认、取消、确认过期、防重复确认。 |
| 下载 | 持久化队列、有限并发、阶段/进度展示、失败重试、运行取消、重启恢复。 |
| 存储 | 单下载根目录、命名与归档、防重名、防越界、重复媒体识别、临时文件处理。 |
| 通知 | 排队、最终成功/失败/取消反馈；通知与下载结果分别记录。 |
| WebUI | 管理员登录、初始化、任务列表与详情、配置管理、基础诊断。 |
| 部署 | Compose、本地 Bot API 服务、持久化目录、权限与空间检查、部署文档。 |

### 3.3 首版暂不包含

- 频道持续监听、历史批量抓取、订阅自动归档。
- 只发送 `t.me` 消息链接后自动访问频道获取媒体。
- 个人 Telegram 账号登录、会话管理及读取仅个人账号有权访问的消息。
- 绕过禁止转发或频道访问限制。
- 多租户、多 Bot、复杂角色、配额和计费。
- 视频转码、在线播放、缩略图媒体库、刮削、字幕与内容识别。
- 任意网站、磁力、网盘等非 Telegram 文件来源。
- WebUI 上传媒体、浏览整台 NAS、删除任意宿主机文件。
- 分布式调度、高可用集群、原生 NAS 安装插件和非 Docker 安装包。

## 4. Telegram 能力边界与调研结论

### 4.1 实际媒体与链接的区别

Bot 收到可访问的实际媒体消息后，可通过文件标识获取文件。转发媒体通常不要求 Bot 先加入原频道；但来源信息可能缺失，不能依赖频道名、原消息地址来完成下载。

直接使用 Telegram 的“转发”功能将频道视频消息转发给 Bot，属于已确认支持的实际媒体输入。复制并粘贴频道消息链接则属于链接输入，即使显示视频预览也不作为实际媒体处理。

仅收到频道消息链接，不等于 Bot 能读取其媒体。首版不解析链接获取媒体，应提示“请将视频或图片直接转发/发送给机器人”，且不创建下载任务。频道禁止转发时，应解释当前输入方式不支持，不承诺绕过限制。

### 4.2 大文件下载

本次已核对 Telegram 官方文档：

- 云端 Bot API 的 `getFile` 下载上限为 20 MB。
- 本地 Bot API Server 支持无该大小上限的下载，并可返回本地文件绝对路径。
- 文档中的“上传最高 2000 MB”是另一项能力，不能误写成此方案的下载上限。

大于 20 MB 的视频下载已确认为首版必须能力，由本地 Bot API Server 提供。默认部署常驻管理组件，可先使用官方云端；选择本地模式时由管理组件启动 API 子进程，代理拓扑另按部署指南配置。实际成功与否仍受 Telegram 可提供的文件、网络、磁盘和设备资源影响，不承诺任意大小均可成功。

本地服务需配置 Bot Token，以及 Telegram API ID、API Hash。后两项用于启动本地 API 服务，不等于登录用户个人账号；部署指南必须说明申请和配置方法。

### 4.3 其他约束

- 照片消息可能包含多种尺寸，保存 Bot 可获取的最大尺寸；不保证与手机中的原始图片字节一致。希望保留原文件时应按文件发送。
- 视频/图片按文件发送时，需同时识别 `document`，不能只处理原生 `video`、`photo`。
- `file_id` 用于获取文件，`file_unique_id` 可辅助去重但不能下载。
- 重试时按需重新获取文件信息，不能把临时下载地址永久当作有效地址。
- 本地 API 可能先完成媒体获取，应用才得到本地文件路径；首版不能承诺始终提供精确的端到端百分比进度。

### 4.4 参考项目与证据范围

参考：[welkin621/tg-bot-video-download](https://github.com/welkin621/tg-bot-video-download)。本次读取其 README，确认其同样用于将转发视频保存到 NAS；依赖 teelebot，并要求本地 Telegram API 服务以下载大于 20 MB 的视频。

本次未审计其源码、安全性、许可证、维护状态及全部功能。可借鉴使用流程和本地 API 思路，不能推定其已具备 WebUI、图片支持、持久化任务等能力。后续复用代码前须核实许可证与依赖兼容性。

## 5. 核心交互流程

### 5.1 单文件

1. 用户向 Bot 发送或转发媒体。
2. 系统校验用户权限，解析媒体类型和可用元数据。
3. 创建“待确认”记录，返回文件信息及“确认下载 / 取消”按钮。
4. 用户确认后，持久化排队任务，反馈任务编号。
5. 后台获取媒体，写入临时文件，检查完成后发布为最终文件。
6. Bot 反馈结果；WebUI 展示同一任务的状态和详情。

信息卡示例：

```text
检测到视频
名称：示例视频.mp4
大小：1.2 GB
时长：12:35
保存位置：2026-10-20/

[确认下载] [取消]
```

文件名、大小、时长、分辨率仅在已知时展示；缺失时省略或标注“未知”，不猜测。确认前只获取必要元数据，不主动触发完整文件下载。

成功反馈至少包含任务编号、保存文件名和相对路径；失败反馈包含明确原因和是否可重试。Bot 默认不展示宿主机绝对路径、凭据或内部堆栈。

点击“确认下载 / 取消”会弹出明确提示，重复点击显示任务当前状态，不重复创建下载。过期后点击任一按钮均提示重新发送媒体；已确认任务的旧“取消”按钮会引导到 WebUI 取消，不会误报已取消。失效或无权限按钮提供通用提示，不泄露其他用户的任务信息。

### 5.2 多文件与媒体组

- “单文件”指一项视频或图片；“媒体组”指 Telegram 中作为一组展示、可通过分组标识关联的多个文件，可包含图片和视频，并非仅指图片集合。
- Telegram 在界面上看似一条多媒体消息，Bot API 通常分多条消息推送；按聊天范围和 `media_group_id` 聚合，展示媒体数量、类型和已知总大小，一次确认。
- 同一媒体组的文件保存在同一独立目录，不因图片/视频类型拆散。单文件采用类型/日归档。互不关联的多条消息不因发送时间接近自动合并；首版不提供手动合并任意消息或导入源目录功能。
- 消息逐条到达，需短暂聚合窗口；时长在原型验证后确定。
- 卡片发出后才到达的迟到项创建新的待确认批次，不自动加入已确认任务。
- 每个文件有独立执行结果，父任务汇总为成功、部分成功或失败。
- 重试默认仅处理失败项；取消保留已完成文件并如实报告。

### 5.3 异常输入

纯文字、链接、不支持类型或无法获取文件标识的消息不进入下载队列，返回简短指引。未授权用户不能创建任务或查看他人任务。

## 6. 功能需求

### F-01 Bot 接入与授权

- 支持设置和校验 Bot Token，显示连通性。
- 必须配置允许使用的 Telegram 用户 ID，不默认向所有人开放下载。
- 首版仅处理私聊，不提供群聊和频道自动接收能力。
- 确认、取消、重试回调校验操作者权限及任务归属，不信任按钮中的任务参数。
- 提供 `/start`、`/help`、`/status` 等少量必要命令，查询仅返回有权访问的任务。

### F-02 媒体解析

- 支持原生视频、照片，以及文件形式的 MP4、MKV、MOV、JPG/JPEG、PNG、WEBP；音频、其他文档、动画/GIF 暂不支持。
- 结合 MIME 与扩展名分类，冲突或不支持时给出明确提示；不要求解码、转码或预览所有格式。
- 记录原始文件名、文件标识、类型、已知大小及可获得的来源信息。
- 说明文字仅作可选元数据，不能直接拼接为可信路径。

### F-03 下载确认

- 必须明确确认后才开始媒体获取，首版不默认自动下载。
- 确认有效期默认 30 分钟，可在 WebUI 配置；从确认卡片发出时计算，创建时固定到期时间。修改配置影响之后创建的确认卡片，过期按钮无效。
- 重复点击、多设备点击和重复事件最多使同一记录入队一次。
- 确认时重新校验权限和配置。目标或 Bot 配置变化时，不能静默使用与卡片不一致的配置。
- 取消后原确认按钮不能再生效。

### F-04 下载与恢复

- 任务、队列和尝试记录持久化，关闭 WebUI 或用户离线不影响执行。
- 默认最多同时下载 3 个文件任务，可在 WebUI 配置；全局限额包含单文件和媒体组子任务，不能按每组重复分配 3 个而超出总限额。这里的并发不要求采用操作系统线程，也不承诺单文件多连接分段下载。
- 显示排队、获取、保存等阶段；有真实数据时显示字节、速度、百分比，否则显示阶段和已用时间。
- 先写临时文件，校验后再发布最终文件，不能把半成品标记成功。
- 已知大小时比对字节数；未知时做基本存在性、写入完成检查，不宣称完整内容校验。
- 排队和运行任务可取消；底层 API 获取若无法立即中断，显示“取消中”，停止后续落盘并清理应用临时文件。
- 网络等瞬时错误退避重试，默认最多自动重试 3 次（首次尝试之外），次数可配置；Telegram 限流遵守 `retry_after`。
- 配置无效、空间不足、权限错误不无限重试，修复后可手动重试。
- 重启保留待确认和排队记录，运行中任务先核对文件再重排或标记需重试。首版不承诺字节级断点续传。

### F-05 存储、命名和去重

- 配置一个容器下载根目录，如 `/downloads`，映射宿主机本地盘或 NAS 已挂载目录。
- 按消息关联优先归档：单文件直接保存到 `YYYY-MM-DD/`；多文件媒体组保存到 `YYYY-MM-DD/<文字摘要或回退名>_<任务短ID>/`，不再添加 videos/images/groups 分类层。组内按消息顺序选择首条非空附带文字作为摘要，缺失时回退到原文件名或媒体类型。摘要折叠空白、移除控制字符，最多 80 字；组目录安全清洗并限制为 180 UTF-8 字节（保留短ID后缀）。新任务标题仅使用摘要或回退名，不追加编号，WebUI 与 Bot 确认、入队、结果提示一致。日期按请求接收时间及配置时区计算，已冻结的待确认请求、已有任务和重试路径保持不变，不搬迁旧目录。列表在标题下显示完整任务编号，Bot 确认、入队、结果和状态提示在独立一行显示完整任务编号，便于区分同名任务。
- 归档时间使用系统接收时间并按配置时区解释，不依赖可能缺失的原始频道时间；组目录在确认时固定，重试继续使用同一目录。
- 优先使用清洗后的原始文件名；缺失时用媒体类型、时间、任务短 ID 生成。
- 处理非法字符、路径分隔符、保留名、超长名，任何输入均不能越出允许根目录。
- 同名不同文件追加稳定后缀，不覆盖已有文件。
- 同一 Bot 范围内按文件唯一标识辅助去重：已有活动任务则返回原任务；已有成功记录且文件存在则提示已保存。
- 文件已被用户移走或删除时允许重新下载，失败记录不能阻止重试。首版不提供强制重复保存。
- 媒体组中命中已有文件时，按全局去重规则跳过，反馈已有路径，不移动或复制原文件；该组需要新下载的文件仍统一写入组目录，反馈中区分新下载、已存在和失败项。
- 不承诺识别所有“内容相同但 Telegram 标识不同”的文件，首版不强制全文件哈希扫描。
- 分别考虑目标目录与本地 API 缓存空间；未知文件大小仍需检查最低剩余空间并处理写满。
- 仅清理本应用拥有的临时文件，不删除用户文件、其他任务文件或仍在使用的 API 数据。
- NAS 掉线、不可写时明确失败，不悄悄保存到备用目录。

### F-06 通知

- 排队成功、最终成功、最终失败、取消均有可理解反馈。
- 进度消息节流，建议编辑原消息，避免逐块发送造成刷屏和限流。
- 文件已保存但通知失败时，下载状态保持成功，另记通知失败并有限补偿。
- 恢复时不重复下载成功文件；通知尽量避免重复，不承诺网络边界严格只发送一次。

### F-07 WebUI

| 页面 | 内容及操作 |
| --- | --- |
| 登录/初始化 | 创建管理员凭据、接入配置、校验结果、未完成步骤提示。 |
| 任务列表 | 名称、类型、大小、状态、阶段/进度、创建时间；状态筛选、名称搜索、分页；已结束任务单条或当前页多选删除。 |
| 任务详情 | 来源（若有）、相对路径、时间、尝试次数、错误、通知状态、媒体组子项。 |
| 设置 | Bot、允许用户、允许下载目录、并发等配置及其生效方式。 |
| 系统状态 | 版本、Bot/API 服务连通性、目录可写性、剩余空间、最近错误。 |

- 可查看待确认记录；下载确认只在 Bot 完成，不引入第二套确认交互。
- 界面默认中文，面向内网访问，支持手机浏览器。
- 支持取消活动任务、手动重试失败项；列表默认按创建时间倒序。
- 删除需确认，仅移除已结束任务的记录展示，保留媒体文件及去重、恢复元数据；活动任务须先取消并等待结束，批量删除整批成功或整批不执行。已删除记录不再出现在列表、详情和 Bot 状态中，旧按钮提示重新发送媒体；未发送的任务通知停止，已发消息不撤回。
- 手机可完成常见操作，状态同时用文字表达，不仅依赖颜色。
- 敏感字段默认脱敏，读取接口不返回完整 Token、API Hash 或密码。
- 首版不做媒体预览、目录树、复杂统计及删除媒体文件功能。

### F-08 配置与生效

| 配置 | 建议入口 | 生效规则 |
| --- | --- | --- |
| Bot Token | WebUI；首次可通过部署参数引导 | 校验后切换接收连接，有活动任务时阻止直接更换 Bot 身份。 |
| 允许用户 ID | WebUI | 后续消息与操作立即校验；已确认任务按已授权执行记录处理。 |
| 下载根目录 | WebUI | 只能选已挂载的允许目录，写入检查通过后影响后续确认任务。 |
| 并发数 | WebUI，默认 3 | 影响后续文件调度，降低时不强杀运行任务。 |
| 确认时限 | WebUI，默认 30 分钟 | 影响之后创建的确认卡片，已发卡片到期时间不变。 |
| 自动重试次数 | WebUI，默认 3 次 | 每次执行尝试序列启动时固定，修改影响之后的任务/手动重试序列。 |
| API ID/API Hash、本地服务参数 | Compose/环境变量 | 重启相应服务；WebUI 显示配置状态及指引。 |
| 宿主机挂载、端口、UID/GID | Compose | 重新部署生效，WebUI 不修改宿主机挂载。 |
| Telegram 代理 | WebUI 提供配置、校验和状态；必要服务参数由 Compose 配套 | 支持代理地址、协议与可选认证，密码脱敏；应用与本地 API 分别验证实际生效情况。底层服务需重启时明确提示，不能显示保存即生效。 |

建议优先级：显式环境变量 > 持久化应用设置 > 默认值。环境变量覆盖的项在 WebUI 标记来源并只读，防止保存后不生效。敏感字段提交空值默认不修改，清除需显式操作。

本地模式的代理配置应覆盖实际连接 Telegram 的本地 API 服务，不能仅给应用访问内部 API 的连接加代理；云端模式由应用直接通过代理访问官方 API 与文件下载地址。HTTP CONNECT / SOCKS5 的具体支持链路见部署指南，内部服务通信默认不走外部代理。

新配置先校验再整体提交，失败保留旧值。任务在确认时固定目标目录和归档规则，运行中修改配置不能改变其保存位置。

## 7. 状态与一致性

| 文件任务状态 | 含义与后续行为 |
| --- | --- |
| 待确认 | 可确认、取消或过期。 |
| 已过期 | 不再接受原按钮，可重新发送媒体。 |
| 排队中 | 等待执行，可取消。 |
| 获取中 | Telegram/本地 API 正在获取媒体。 |
| 保存中 | 写入/复制目标目录，校验并发布后成功。 |
| 等待重试 | 等待退避时间，可取消。 |
| 取消中 | 正在停止和清理，不能提前声称已停止。 |
| 成功 | 最终文件完成落盘且状态持久化，通知独立处理。 |
| 失败 | 停止自动尝试，可手动重试并保留尝试历史。 |
| 已取消 | 已停止且临时文件处理完毕，不自动恢复。 |

媒体组另设“部分成功”汇总状态，每项结果可追溯。取消与文件发布同时发生时，以实际发布结果和原子状态更新为准，不同时向用户报告成功与已取消。

必须保证：

- 重复确认、重复 update 和重试不会产生相同的多个活动任务。
- API 请求成功不等于文件保存成功。
- 对“记录已写但文件未发布”和“文件已发布但记录未写”两个崩溃窗口，启动时均能核对和修复状态。
- Bot 与 WebUI 使用同一任务事实来源，不维护两套冲突状态。
- 单 Bot 只运行一个有效接收实例，首版不支持多副本并行消费。

## 8. Docker 与 NAS 部署

### 8.1 推荐拓扑（技术建议）

```text
Telegram 用户 / Telegram 网络
              ↕
本地 Telegram Bot API 服务
              ↕ 内部网络 / 受控文件共享
应用服务：Bot 接收、任务处理、管理 API、WebUI
    ├─ 应用数据：数据库、设置、日志
    └─ 下载目录：宿主机本地盘 / NAS 挂载目录
```

- Compose 默认启动应用及 API 管理组件，本地子进程按 WebUI 设置启动；模式切换和进程恢复无需重建容器。采用长轮询接收，减少公网域名和 webhook HTTPS 要求。
- 默认仅发布 WebUI，API 服务端口留在内部网络。主要面向飞牛 OS 局域网访问，Compose 提供可配置的宿主机绑定地址和端口；不要求公网域名。WebUI 必须鉴权，不自动配置路由器端口映射。
- 持久化应用数据、下载目录、本地 API 数据/缓存，明确各目录权限。
- 若使用本地 API 返回的路径，两容器须有兼容的共享路径；不能假设服务容器路径对应用天然可见。
- 若改为 HTTP 获取/流式传输，需先验证大文件、进度和取消行为；开发前选定主路径。

### 8.2 运维要求

- 提供 Dockerfile、Compose 示例、无真实凭据的 `.env.example`，并提供飞牛 OS 的部署与目录权限说明。
- 提供 Bot 创建、API ID/Hash 配置、用户 ID 获取、NAS 挂载与 UID/GID、网络代理排错说明。
- 提供备份、升级、配置迁移、恢复、停止服务指南。
- 本地 API 可能先缓存再复制，峰值可能同时占用两份媒体空间；同盘/跨盘均需分别预算。
- 明确缓存保留、清理责任及所选镜像支持的清理方式，不直接删除运行中的 API 数据。
- 数据库优先放可靠本地文件系统，避免未经验证的网络盘文件锁行为。
- 健康状态区分进程正常、初始化完成、Telegram 可达、目录可写；依赖故障时 WebUI 保留诊断能力。
- 正常停止时停止派发新任务并保存状态；日志轮转，避免长期运行写满系统盘。
- 默认保留任务历史与下载媒体，不自动删除媒体；应用临时文件和本地 API 缓存按安全策略清理，不把缓存保留当成永久媒体归档。
- 建议支持 Linux amd64、arm64，但需验证整套镜像及目标设备；不能只看应用镜像便宣称支持。

## 10. 技术候选与模块边界

以下技术路线已在技术设计中细化，待最终规划评审；精确依赖版本在实施 M0 锁定。架构、数据模型、接口和配置契约以链接的技术设计为准。

| 部分 | 建议 | 理由与条件 |
| --- | --- | --- |
| 后端 | Python + FastAPI | 适合异步任务与管理接口，无现有工程约束。 |
| Bot 库 | 如 aiogram 等成熟库 | 必须支持自定义 API Base URL，先验证本地路径、超时等行为。 |
| 数据 | SQLite | 单实例降低运维负担，数据库卷使用可靠文件系统。 |
| 调度 | 持久化队列 + 有限进程内 worker | 首版无需 Redis/Celery，仍必须实现领取、幂等与恢复。 |
| WebUI | Vue 3、TypeScript、Vite、Element Plus | 中文轻量管理界面，构建产物由后端服务，减少部署组件。 |
| 更新 | 轮询 | 首版足够，必要时再引入 SSE/WebSocket。 |
| 文件获取 | 本地 Bot API Server | 大文件能力依赖真实原型验证。 |
| 可选网络代理 | 云端 HTTPS / TDLib 原生 HTTP CONNECT 与 SOCKS5 | 同一份 WebUI 配置，固定本地 API 源码补丁，不需要 TUN，仍需真实代理链路验收。 |

建议模块：Telegram 接入、媒体解析、确认授权、任务调度、文件保存、通知、配置、管理 API。Bot 和 WebUI 共用业务服务。

后续数据设计至少覆盖：媒体请求/媒体组、文件项、任务、执行尝试、通知记录、配置版本、管理员凭据；存储 update/message 标识辅助幂等。时间统一存 UTC，展示按时区转换。
